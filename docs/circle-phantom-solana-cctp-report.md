# Phantom Solana CCTP Route Report

Date: 2026-06-13  
Project: QuantumBridge  
Environment: Testnet only  
Status in QuantumBridge: Phantom is locked for Solana CCTP routes pending SDK/wallet compatibility review.

## Summary

QuantumBridge tested Phantom on Solana Devnet CCTP routes using Circle App Kit and the Solana Kit adapter. Backpack and Solflare complete the same Solana CCTP flows successfully, but Phantom consistently fails at the source burn stage after wallet signing.

The latest observed failure is a `burn` step simulation failure with no burn transaction hash. Because `txHash` is `null`, no USDC is burned and no recovery action is required for that attempt.

QuantumBridge has locked Phantom for Solana CCTP routes in the UI to prevent user confusion while this is reviewed.

## Observed Event

Captured from `kit.on("*")` event logging after signing both Phantom wallet prompts:

```json
{
  "protocol": "cctp",
  "version": "v2",
  "traceId": "110f0fa6d08a5722a30f51650cf54f81",
  "method": "burn",
  "values": {
    "name": "burn",
    "state": "error",
    "txHash": null,
    "forwarded": false,
    "error": {
      "name": "ONCHAIN_SIMULATION_FAILED",
      "code": 5002,
      "productMessage": "Phantom signed, but the source burn simulation failed before submission. No USDC was burned; try again or use Backpack/Solflare for this route."
    }
  }
}
```

## Expected Behavior

After Phantom signs the required Solana transaction flow, the SDK should either:

- submit a valid source burn transaction and emit a burn `txHash`, or
- return a wallet-specific/actionable error before the user signs, if Phantom cannot support this transaction shape.

## Actual Behavior

Phantom proceeds through wallet signing, then the Circle/App Kit event stream reports:

- method: `burn`
- state: `error`
- error name: `ONCHAIN_SIMULATION_FAILED`
- code: `5002`
- txHash: `null`

This leaves the user with no submitted burn and no recovery path, because the transfer never reached the on-chain burn checkpoint.

## Product Impact

For end users, the confusing part is that Phantom appears to sign, but the bridge does not submit a burn. This can feel like a stuck bridge even though funds never moved.

QuantumBridge now handles this safely by:

- showing a product message that no USDC was burned,
- avoiding creation of a recovery checkpoint for this failed-before-burn case,
- keeping Phantom visible but locked in the Solana wallet list,
- recommending Backpack or Solflare for Solana CCTP routes.

## Current Workaround

Use Backpack or Solflare for Solana CCTP source or destination routes. Both have worked successfully in QuantumBridge testing.

For Solana destination routes, QuantumBridge is also testing Circle Forwarder support so the destination mint can be completed without requiring a Solana wallet signature.

## Request For Circle Dev Team

Could the Circle team confirm whether Phantom is expected to support the Solana CCTP transaction shape generated by `@circle-fin/adapter-solana-kit`?

If Phantom is not supported, it would help to have one of the following:

- official wallet compatibility guidance for Solana CCTP routes,
- a preflight capability check before signing,
- a clearer SDK error that identifies the wallet compatibility issue before users approve transactions,
- recommended adapter/provider handling for Phantom if a different signing path is required.

## Reproduction Notes

1. Connect Phantom as Solana wallet on Solana Devnet.
2. Connect an EVM wallet for the destination side where needed.
3. Start a Solana CCTP transfer in QuantumBridge.
4. Approve/sign the Phantom prompts.
5. Observe the `burn` event fail with `ONCHAIN_SIMULATION_FAILED`, code `5002`, and `txHash: null`.
